INCUBRIX ENGINEERING ASSESSMENT 2
Prompt-Based Video Editing Engine
Edit a video by typing what you want - and keep every edit correct as the conversation goes on
Thank you for applying to IncuBrix
IncuBrix helps creators make videos with AI. In this assessment you will build one real piece of our product: the editing
engine behind the IncuBrix Editor. Please read the whole brief once before you start.
At a glance
What you build An editing engine that turns plain-language instructions ("cut out the ums, remove the part about
pricing, add a caption on the intro") into exact, reversible edits on a video, and renders the result.
Why it matters Creators lose hours dragging clips on a timeline. Typing what they want is faster, but only if every edit
stays correct when edits pile up.
What you hand over A containerised API service, a session-runner tool, a live demo URL, your code, a short report and a
test pack.
Time allowed 10 calendar days from the day you receive this brief. The exact deadline is in the email.
Tools allowed Anything: any AI coding assistant, model, API, cloud or library. Just disclose it and keep it
commercially usable.
How you are selected You fill in a Submission Form showing what works, with proof. We verify it and run 5 hidden tests
(screening, 80 marks), then hold a 60-90 minute live session (20 marks) with the strongest candidates.
Shortlist: 75+. Top pick: 85+.
How to use this brief
1. Read The problem and What you build to understand the job.
2. Build the Must-haves first. Each one is pass or fail, and every one must pass.
3. Then climb the Levels: Core is required; Advanced and Outstanding earn more marks.
4. Follow the Integration Standard so your work can plug straight into our product.
5. Fill in the Submission Form (Excel file sent with this brief) as you go. It is how you show us your work, and it is the
main thing we review.
The problem
A creator uploads a talking-head video (a podcast, tutorial or interview) and edits it by typing. Applying one instruction
once is easy. The real problem is a conversation of edits: the creator keeps adding instructions, refers back to earlier
ones ("make that caption bigger"), changes their mind ("actually, put the pricing part back"), is vague ("remove the
boring bit"), and every edit shifts the timing that later edits depend on.
The single most important rule
Edits belong to content, not to a clock position. A caption added on the words "welcome to the channel" must stay on
exactly those words after anything before it is cut, sped up or moved. If you store it as "1:40", it will silently land on the
wrong words after the first cut.

What you build
(cid:127) Video intake: accept MP4 or MOV at any common resolution and frame rate; read duration, frame rate and audio.
(cid:127) Transcript: word-level timing for every word, with start, end, speaker and confidence. Use any speech-to-text tool, but
handle its mistakes.
(cid:127) Your own timeline format: the edited video described as data, with a JSON Schema. Designing this well is a large part
of the problem.
(cid:127) Editing engine: turns instructions into structured operations on the timeline.
(cid:127) Rendering: produces the final video from the timeline, as a separate step.
(cid:127) Session runner: a command-line tool that plays a scripted editing session (format below) and writes every response.
We test every submission with it.
Operations to support
Cut a range; keep only a range; reorder sections; speed up or slow down a range; mute or bleep words; add a caption or
text overlay; auto-caption the whole video; remove filler words (um, uh, and "like" only when used as a filler); remove
silences longer than N seconds; add background music that automatically gets quieter under speech; undo and redo;
restore one specific earlier edit.
Every instruction gets exactly one of three answers
Answer What it must contain
Applied The list of operations performed and a before/after summary (for example new length, what moved).
Needs clarification A specific question with options, for example "Pricing is mentioned at 1:05, 2:40 and 3:15 - which one,
or all?". Never guess on anything destructive.
Rejected The reason: impossible, out of range, or contradicts an earlier edit (and which one).

How it must plug into IncuBrix (Integration Standard)
IncuBrix runs its services as containers that talk to each other over HTTP APIs. If your submission follows the ten points
below, we can connect it to the product without rewriting it. Each point is worth 2 marks (20 marks in total). Tick each
one in your Submission Form with a link to the proof.
Requirement What exactly we check
1. One-command start docker compose up starts the service and everything it needs (database, storage, local test
and test servers). One command runs all tests (unit, integration and at least one end-to-end) with no API keys.
A .env.example lists every setting.
2. Documented HTTP An openapi.yaml (OpenAPI 3.1) that matches the running service exactly. All routes under
API /api/v1/.
3. Background jobs Anything slower than 2 seconds runs as a job: POST returns 202 with a job_id; GET
/api/v1/jobs/{job_id} returns status (queued, running, succeeded, failed), progress 0-100 and
result links. Optional callback URL, signed with HMAC-SHA256 in an X-IncuBrix-Signature
header.
4. Safe retries An Idempotency-Key header on every POST: sending the same request twice with the same key
returns the same job and never does the work twice.
5. Clear errors Errors are JSON: {"error": {"code", "message", "retryable", "details"}}. Codes
are UPPER_SNAKE_CASE and listed in the README.
6. Configuration All settings, paths, model names and limits come from environment variables or a config file. No
hard-coded paths or keys.
7. Files in, files out Inputs accepted as an upload or a URL. Outputs saved to S3-compatible storage (MinIO in the
compose file is fine) and returned as download links.
8. Logs and health Structured JSON logs with timestamp, level, job_id and the X-Correlation-Id from the request.
GET /health and GET /ready endpoints.
9. Output manifest Every result includes a JSON manifest: which models/providers and versions were used, settings,
seed, timings, cost estimate, warnings, and licence/rights information.
10. Batch runner A command-line tool that runs a folder or file of test inputs against the API and writes all results to one
folder. We use this to test every submission the same way.

Metric How to measure it
Instruction latency Median and slowest response time per instruction on a 5-minute and a 60-minute video

Word clipping Number of cuts that clip part of a word, from a listening check of 20 cuts.
